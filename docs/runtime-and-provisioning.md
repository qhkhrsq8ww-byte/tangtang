# Python 运行环境与新机器初始化

本文针对 2026-10-20 团队克隆测试发现的运行时兼容和新环境配置缺口。目标是避免 V4 在 Python 3.8 环境中启动后静默失效，并避免新克隆因缺少本机数据而被误判为功能完整。

## 1. 运行时版本策略

- V4 核心使用 `zoneinfo` 和新式类型注解，统一要求 **Python 3.10 或更高版本**；建议使用 Python 3.11。
- 旧 Mac 若 `/usr/bin/python3 --version` 显示 3.8.x，不能用它运行 V4。不要通过零散修改类型注解来假定全仓已兼容 3.8。
- 生产环境在新解释器安装完成、回归测试通过之前，继续使用已验证的直连版 `code/cat/cat-chat.py`。不要为了测试 V4 覆盖正在工作的生产文件。
- CI 运行的是合成数据单元测试，不连接真实家庭数据、密钥、麦克风、音箱或投影仪；CI 通过不等于 Mac 实机验收通过。

## 2. 新克隆后的安全初始化

新克隆中缺少密钥、家庭配置和运行时记忆是预期行为，不要将这些文件提交到 Git。

1. 在独立目录安装 Python 3.11，并确认 `python3.11 --version`。
2. 从可信的本机备份或安全存储中恢复所需配置；不要从仓库、聊天记录或日志复制真实密钥。
3. 按需恢复的本机文件包括 `.llm_key`、`cat-stt-config.sh`、`cat-state.json`、`cat-memory.json`、`cat-chat-history.json`、`cat-habits.json` 和 `data/family.json`。仅恢复当前功能确实需要的文件。
4. 对密钥文件设置最小权限，例如 `chmod 600 .llm_key cat-stt-config.sh`。不要把真实值写进命令行参数、终端截图或报告。
5. 确认家庭数据目录、模型配置和音频设备后，再进行本机集成测试。

## 3. 合并前自动检查

GitHub Actions 的 V4 workflow 应完成以下检查：

- 在 Python 3.10 和 3.11 上运行 V4 单元测试；
- 对仓库 Python 源码执行编译检查；
- 对仓库 Shell 脚本执行 `bash -n`；
- 任一检查失败时，工作流必须失败，不允许以“代码能提交”代替测试通过。

仓库内的 `tests/smoke-20261019.sh` 是面向已配置 macOS 生产主机的冒烟测试，会检查本机密钥、LaunchAgent、运行目录及 repo/live 漂移。不要把它直接当作全新克隆环境的 CI 测试；新克隆应先运行不依赖真实家庭数据的单元与静态检查。

## 4. V4 上线验收清单

- [ ] 生产目录中的实际入口文件已确认，且回滚副本可用。
- [ ] 运行 V4 的解释器版本为 Python 3.10+，LaunchAgent/启动脚本使用该解释器的明确路径。
- [ ] 发声门控成功、拒绝发声、成员信息缺失和异常退出场景均有测试；门控异常应可观测，不能只表现为“糖糖没反应”。
- [ ] 有效配置时能得到非兜底回复；缺少配置时会给出可诊断的降级状态。
- [ ] 私密内容和未知说话人策略保持默认拒绝出网，除非经过明确授权。
- [ ] 任务派发跳过、锁冲突、计划/任务同步失败等状态不会误报健康。
- [ ] Mac 实机完成语音输入、回复生成、语音播报和投影联动测试。
- [ ] 回归结果、实际 Python 路径、入口文件版本和回滚方式已记录。

**回滚原则：** 如果 V4 任一上线验收项失败，恢复已验证的直连版和既有启动配置；不要在生产环境中边修兼容边试运行。
